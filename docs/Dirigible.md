# Dirigible — dedicated hardware controller for Lee

> A physical device on your desk that connects to Lee. Not a phone app, not a
> remote desktop — a purpose-built control surface for your IDE.

## Overview

**Dirigible** is a LilyGO T-Deck running firmware that connects to one or more
Lee instances over the LAN. It shows the live tab list, lets you focus a tab,
gives you one terminal you can type into, and asks Hester a question without
touching your keyboard.

Where Aeronaut puts Lee in your pocket, Dirigible puts Lee on your desk — a
persistent, glanceable, tactile interface that doesn't compete with your
phone's attention or battery.

### Naming

**Dirigible** — a steerable airship. Lee Scoresby's balloon was a dirigible,
not a passive hot-air balloon: it had propulsion and control surfaces.

The quartet:

- **Lee** — the editor (the balloon, the vehicle)
- **Hester** — the daemon (the intelligence, the awareness)
- **Aeronaut** — the mobile companion (the vantage point from afar)
- **Dirigible** — the control surface (the physical interface, the helm)

## Hardware

One shipped tier: the **LilyGO T-Deck** (ESP32-S3). Everything else that once
appeared in this document — Linux SBCs, the ESP32-P4, LEDs, NPU voice work,
Hester pushing to the device — is parked in [Ideas](#ideas-not-planned).

| Component | Spec |
|-----------|------|
| SoC | ESP32-S3 (dual Xtensa LX7 @ 240 MHz) |
| RAM | 512 KB SRAM + 8 MB octal PSRAM |
| Flash | 16 MB |
| Display | 2.8" 320x240 IPS, ST7789 over SPI |
| Touch | GT911 capacitive, I2C |
| Keyboard | BlackBerry-style QWERTY behind an ESP32-C3 keypad MCU, I2C 0x55 |
| Pointer | Optical trackball, 5 GPIOs (4 directions + click) |
| Battery | LiPo with a 2x divider on ADC1 GPIO 4 |
| Radio | WiFi 4 + BLE 5 (LoRa socket unpopulated on this unit) |

Pin assignments and the empirically derived display/touch transforms live in
`dirigible/platform/esp32/components/tdeck-bsp/include/tdeck_board.h`.

## Architecture

```
dirigible/
├── core/                       portable C++17, no ESP-IDF
│   ├── LeeConnection           /context/stream WebSocket + POST /command
│   ├── PTYClient               /pty/<id>/stream WebSocket
│   ├── HesterClient            POST /context/stream, SSE phase/response parser
│   ├── MachineManager          multi-machine state, health pings, tokens
│   └── models / EventBus       LeeContext parsing, in-process events
├── platform/esp32/components/
│   ├── dirigible-core          wraps core/ as an ESP-IDF component
│   ├── dirigible-esp32         core's transports on esp_websocket_client /
│   │                           esp_http_client / mdns, STA WiFi, NVS config
│   └── tdeck-bsp               board bring-up: ST7789, GT911, keyboard,
│                               trackball, battery, LVGL glue
├── firmware/                   the ESP-IDF project (main/, sdkconfig.defaults,
│                               partitions.csv)
└── tools/dirigible-provision/  host-side NVS provisioning over USB
```

`core/` is deliberately free of ESP-IDF so the protocol layer can be compiled
and exercised on a host; everything platform-specific sits behind
`ITransportFactory`, `IConfig` and `IDiscovery` in
`core/include/dirigible/transport.hpp`.

The firmware is plain ESP-IDF + LVGL 8. It was previously generated by the
**screenschema** framework from a YAML schema; that dependency is gone (see
[History](#history-the-screenschema-decoupling)).

## Build, flash, provision

Requires ESP-IDF **v5.4**.

```bash
source /path/to/esp-idf/export.sh
cd dirigible/firmware
idf.py set-target esp32s3      # first time only
idf.py build
idf.py -p /dev/tty.usbmodem1101 flash monitor
```

The first `set-target` (or `build`) resolves managed components from
`components.espressif.com` — `lvgl/lvgl` (8.x), `espressif/esp_lcd_touch_gt911`,
`espressif/esp_websocket_client` and `espressif/mdns` — so that step needs
network access. Afterwards `firmware/managed_components/` is self-contained.

Flash layout (`firmware/partitions.csv`, 16 MB):

| Partition | Type | Offset | Size |
|-----------|------|--------|------|
| `nvs` | data/nvs | 0x9000 | 24 KB |
| `otadata` | data/ota | 0xf000 | 8 KB |
| `ota_0` | app | 0x20000 | 6 MB |
| `ota_1` | app | 0x620000 | 6 MB |
| `storage` | data/fat | 0xC20000 | ~4 MB |

`dirigible-provision` writes the NVS partition at 0x9000, so the offset must
stay put.

### Provisioning over USB

Useful when you'd rather not type a token on a thumb keyboard:

```bash
source /path/to/esp-idf/export.sh
cd dirigible/tools/dirigible-provision
python3 dirigible_provision.py wifi set MySSID hunter2
python3 dirigible_provision.py machine add studio 192.168.1.10 \
    --token "$(cat ~/.lee/api-token)"
python3 dirigible_provision.py flash --port /dev/tty.usbmodem1101
```

It writes only the NVS partition, so the app image is left alone.

### NVS layout

| Namespace | Key | Type | Meaning |
|-----------|-----|------|---------|
| `ss_wifi` | `ssid`, `password` | str | WiFi credentials |
| `dirigible` | `mach_count` | u8 | number of machines |
| `dirigible` | `m<i>_name`, `m<i>_host`, `m<i>_user` | str | machine record |
| `dirigible` | `m<i>_lee_port`, `m<i>_hester_port` | u16 | ports |
| `dirigible` | `tok_<name>` | str | cached bearer, key truncated to 15 chars |

The `ss_wifi` namespace name is historical — it came from screenschema — and
is kept so already-provisioned devices keep booting.

Tokens are stored in **plaintext** unless flash encryption plus NVS encryption
are enabled. See [Security](#security).

## Pairing

On first boot (no WiFi credentials, or no machine record) the device opens the
pairing flow. Reach it later from the menu: hold the trackball.

1. **WiFi** — pick a network from the live scan (`#` marks a secured one).
2. **Password** — type it; Enter connects and saves it to NVS.
3. **Find Lee** — the device runs an mDNS PTR query for `_lee._tcp` and lists
   what answers; pick one, or choose **Manual entry** and type `host` or
   `host:port` (default 9001).
4. **Token** — type the Lee API token.

The token is typed rather than discovered on purpose: Lee's `_lee._tcp`
advertisement carries the instance name, host and port but deliberately **no**
`token` TXT record, because anything on the LAN can read a TXT record. Get the
token from Lee's pairing dialog, or `cat ~/.lee/api-token`.

The token is persistent across Lee launches (punch-list item 2), so a
provisioned device stays paired.

## Screens and input

| Screen | What it does |
|--------|--------------|
| **Tabs** | Live list of Lee's tabs from the context stream. Selecting one sends `system.focus_tab`; if the tab owns a PTY it also opens the terminal on it. |
| **Terminal** | A character grid over the PTY WebSocket. ESC returns to Tabs. |
| **Hester** | One input line. Enter streams the ReAct phases, then the answer. |
| **Pairing** | The flow above. |

A 16 px header carries the machine name, a link dot and battery percentage; a
14 px status bar carries the last message and the current screen.

| Input | Effect |
|-------|--------|
| trackball roll | moves the LVGL pointer; rolling into a screen edge scrolls what's under it |
| trackball click | activates whatever the pointer is over |
| trackball hold (0.8 s) | opens the menu: Tabs / Hester / Pairing / Reconnect |
| trackball in Terminal | acts as a d-pad, one detent per arrow key |
| ESC | leaves Terminal; steps back through Pairing |
| touch | works anywhere the pointer does |
| every other key | typed into whatever has focus, or straight to the PTY in Terminal |

**Sym+key chords are not available.** The T-Deck's keypad MCU applies the Sym /
Alt / Shift layer itself and reports one already-resolved ASCII byte over I2C,
so the firmware cannot tell Sym+X from the symbol X produces. A Sym-based
shortcut layer would need custom keypad firmware. The trackball long-press is
the menu affordance instead.

### The terminal

Not a wrapping label: a real COLS×ROWS cell buffer (`firmware/main/vt.cpp`)
painted as one LVGL label per row in `lv_font_unscii_8`. Grid size is measured
from the font at boot rather than assumed. `lv_font_unscii_8` reports an
8 px advance and a 9 px line height, so the 320x210 content area gives
**40 columns x 23 rows**. That size is sent upstream as
`{"type":"resize","cols":40,"rows":23}` on the PTY WebSocket, which
`api-server.ts` forwards to `PtyManager.resize()`.

The parser handles CR, LF, BS, TAB, FF; `ESC M`, `ESC 7`/`ESC 8`, charset
selection; and the CSI sequences that move or erase — CUU/CUD/CUF/CUB, CNL/CPL,
CHA, VPA, CUP/HVP, ED, EL, IL/DL, DCH, ICH, SU/SD, DECSTBM, SCP/RCP. SGR is
parsed and discarded (the panel is monochrome by choice), OSC is consumed up to
BEL or ST, and anything else is swallowed. There is no colour, no attribute
rendering, no alternate-screen bookkeeping, no scrollback, no mouse reporting.
Bytes ≥ 0x80 render as blanks, because the lifted font is ASCII-only and LVGL
labels require valid UTF-8.

## Wire protocol

Everything is authenticated with Lee's persistent API token
(`~/.lee/api-token`, mode 0600, written by `APIServer.loadOrCreateAuthToken()`).

| Direction | Endpoint | Auth |
|-----------|----------|------|
| device → Lee | `ws://host:9001/context/stream?token=…` | token query param |
| device → Lee | `ws://host:9001/pty/<id>/stream?token=…` | token query param |
| device → Lee | `POST http://host:9001/command` | `Authorization: Bearer …` |
| device → Lee | `GET http://host:9001/health` | open (used for the 15 s liveness ping) |
| device → Hester | `POST http://host:9000/context/stream` | `Authorization: Bearer …` |

Context messages are `{"type":"context_update","data":{…LeeContext}}`. PTY
messages are `{"type":"data","data":"…"}` and `{"type":"exit","code":N}`;
anything the device sends that isn't JSON is written to the PTY verbatim, and
`{"type":"resize","cols":C,"rows":R}` resizes it.

Commands follow Lee's unified API: `{"domain","action","params"}`. Dirigible
uses `system.focus_tab`, `system.close_tab`, `editor.open`, `editor.save` and
`tui.<type>`.

Hester's SSE stream emits `event: phase` (`{"phase","iteration","tool_name"}`),
`event: response` (`{"text","session_id"}`), `event: error` and `event: done`.

**Known mismatch:** Hester's `ContextRequest.source` is typed
`Literal["Lee","Slack","CLI"]`, so a request tagged `"Dirigible"` is rejected
with a 422. The device sends `"Lee"` until that Literal is widened.

## Security

- The bearer token is the only credential. Anything that can reach :9001 or
  :9000 with it can drive the editor, so keep both on a trusted LAN.
- Tokens and the WiFi password sit in plaintext NVS. They are only protected if
  the firmware enables flash encryption plus NVS encryption
  (`CONFIG_NVS_ENCRYPTION` and an `nvs_keys` partition). Not enabled today.
- `~/.dirigible/config.yaml` on the provisioning host holds the same secrets;
  `dirigible-provision` chmods it 0600.
- Machine names longer than 11 characters share a truncated `tok_` NVS key, so
  two such machines would collide on the cached token. The pairing flow
  truncates names to 11 characters to make the collision visible rather than
  silent.
- No TLS: `ws://` and `http://` only, matching Lee's LAN-only API server.

## History: the screenschema decoupling

Dirigible's firmware used to be generated by
[screenschema](https://github.com/Intrafocal/screenschema), a YAML-driven UI
framework, with the T-Deck HAL, the LVGL port, the transports and a brookesia
app shell all coming from a git submodule. screenschema was built to drive
several projects; it ended up driving one, and it has been retired.

Dirigible now owns the parts it used:

- the **T-Deck HAL** was lifted verbatim into
  `platform/esp32/components/tdeck-bsp/` — ST7789 init with LILYGO's gamma
  tables, the rotation-3 transform, GT911 panel-IO framing and calibration, the
  shared-I2C discipline, the trackball-as-pointer driver with its visible
  cursor and edge scrolling, the keypad reader, the battery ADC, and the 16 KB
  main-task stack. Every file carries its source path and the screenschema
  commit it came from (`76b6ce9`).
- the **runtime wrappers** (SSWebSocket, SSHttpClient, SSMdns, SSWifiManager,
  SSInput, SSBattery, SSFonts) were reimplemented directly on
  `esp_websocket_client`, `esp_http_client`, `mdns` and `esp_wifi` in
  `platform/esp32/components/dirigible-esp32/`.
- the **brookesia phone shell**, the YAML schema, the widget factory, the
  codegen templates and the OTA/gateway/device-server machinery were dropped
  outright.

screenschema remains its own repository; Dirigible no longer references it and
the submodule is gone.

## Ideas (not planned)

Everything below was in the original specification and is not being built. It
is kept because the reasoning is still useful if the scope ever widens.

### A Linux tier

A **Luckfox Pico Ultra** (Rockchip RV1106G, 256 MB RAM, onboard WiFi, 0.5 TOPS
NPU) behind a 4" 720×720 MIPI DSI touch panel, with an M5Stack CardKB over I2C,
would make a desk-mounted Dirigible with a real GUI and native SSH. The
attraction was running the same Python tooling as the host and reaching
machines over SSH the way Bridge does, rather than only over Lee's HTTP API.
The cost is a second, entirely different firmware and UI stack for one extra
screen size.

A Raspberry Pi Pico 2 W was sketched as a sub-$10 status-only variant; 520 KB of
SRAM rules out terminal rendering.

### ESP32-P4 and C6

The P4 (RISC-V, MIPI DSI, no radio — pairs with a C6 over SDIO for WiFi 6) was
the path to a larger, higher-resolution handheld. The lifted BSP is T-Deck
specific; a P4 would need its own display driver and a hosted-WiFi transport,
both of which screenschema had and which were deliberately not carried over.

### LED status indicators

An RGB LED or a small strip reflecting build state, idle time, or Hester
activity — glanceable without waking the screen. Needs a status vocabulary in
the context stream that doesn't exist yet.

### On-device voice

Microphone capture into the NPU for wake-word detection, then a spoken query to
Hester. The T-Deck has an I2S mic and speaker and screenschema had drivers for
both; the missing pieces are wake-word inference the S3 can afford and a
round-trip latency worth the ceremony.

### Hester → device push

Today the device pulls: it opens a WebSocket and asks. The inverse — Hester
pushing a notification, or steering the device's screen the way it steers Lee's
UI — would need an HTTP server on the device and a device registry on the Lee
side. screenschema had exactly this (`SSDeviceServer`, `SSNotification`,
`_screenschema._tcp` advertisement); it was dropped with the rest because
nothing used it.

### Multi-machine

`MachineManager` already models several Lee instances with per-machine tokens
and health pings, and NVS stores a list. The UI only ever drives machine 0. A
machine picker in the menu is a small job whenever a second machine exists.

### Desk mode

A 720×720 dashboard layout — git status, running services, recent Hester
answers, a clock — as opposed to the handheld list-and-terminal layout. Tied to
the Linux tier above.
